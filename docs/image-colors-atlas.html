Architecture as built

client-heavy · 3 stores

All analysis runs in the browser. Netlify Functions exist only for persistence and for a learning API the UI mostly never calls. There is no pages/ directory: the README's /train page does not exist; everything is modals over one app.vue.

Domain model

CONTEXT.md · glossary
keep the existing words

Decision (Hiren, 2026-09-06): no wholesale rename. The glossary keeps the words the code and UI already use — Preset, Processed Image, Analysis Settings, Parent Color, Pantone Match, Feedback, Play Mode, Knowledge Base — and standardises only where one word means two things (“color family” = HSL hue bands and parent colours) or two names mean one thing (calculateConfidence returning a score in one file and a distance in another). The diagram below shows the concepts and their relations under those names; the boxes marked “later” are structural splits to make only when the feature that needs them (re-analysis history, mood ratings) is actually built.

Two conflicts to resolve in code: (1) ColorFamilyBreakdown.vue groups colours by HSL hue bands and calls them “families” — the glossary reserves the matcher's anchors as Parent Color; rename the HSL grouping “Hue Group” or drop it. (2) calculateConfidence returns a 0–100 score in services/colorUtils.js and a raw CIE76 distance in composables/useColorUtils.js; the second one is a Distance and should be named so.

On determinism: Hiren prefers seeing run-to-run variation from the random initialisation, so seeding becomes an Analysis Setting (“reproducible run”, default off) rather than a forced fix. The RGB/LAB counting mismatch (§ 3) is a separate defect and stays a must-fix: it changes percentages systematically, not randomly.

Target persistence: VAMS

koala/VAMS · Laravel 11 · Postgres 15
same Spaces bucket

VAMS already has the primitives: user-defined Entry Types with a JSON field_config, Entries with a native Postgres json content column, entry_relation and image_collection fields, and file storage on the very same bengijzel bucket — which is why the Strapi migration is JSON-only: every sourceImage URL already points into that bucket and nothing needs re-uploading. What VAMS lacks is a way to write to it from another app. The Entry Type names below follow the earlier proposal; under the keep-the-words decision they map 1:1 to preset, processed-image, parent-colors (see docs/cms-data-model.md, “Migration”).

VAMS changes required, in order

  1. Write API — POST/PATCH/DELETE /api/v1/entries with Sanctum tokens (installed; routes commented out in routes/api.php). Today the API is read-only; all writes are session + CSRF.
  2. json field type — passthrough in EntryValidationService; currently unknown types coerce to string.
  3. API file upload with preserve_original (VAMS converts ≥ 2 MB images to WebP — must not touch analysis sources).
  4. Owner reads of unpublished entries — API filters to published only (EntryService.php:95–121).
  5. Batch create (≤ 50) and a higher throttle than 60/min for token clients.
  6. CORS — config/cors.php combines '*' with supports_credentials; list Netlify origins explicitly.
  7. Seeder for the nine Entry Types — today types are admin-UI only.

Migration path from Strapi and the full field tables: docs/cms-data-model.md.
